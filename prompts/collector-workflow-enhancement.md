# Implementation Prompt: ReLoop Collector Workflow Enhancement

## Goal
Extend the existing ReLoop Collector experience into a mobile-first, end-to-end workflow. Modify the existing app; do not rebuild it or create parallel collection, notification, assignment, map, or authentication systems.

## Existing implementation
- Collector navigation and screens already exist in `client/app/page.tsx` and `client/app/workflow-screens.tsx`. Collection data and requests are in `client/lib/dashboard-api.ts`.
- The client polls role workflows every 3 seconds while on the dashboard, tracking, rewards, collector board, and collector pickups.
- `server/src/features/collections/collections.routes.ts` already scopes collector collection reads to that collector's active/completed assignments and checks collector ownership before accept, decline, progress, and weight operations. All collection routes require authentication. Recycler responses redact exact collector coordinates.
- The existing lifecycle is assignment -> accept (`COLLECTOR_ON_THE_WAY`) -> arrive -> collect -> facility verification. Pause/resume already exist, but pause has no required reason. Collector decline currently stores free text; it notifies the recycler and Admin and leaves reassignment for Admin.
- `CollectorProfile.availability` persists `AVAILABLE`, `UNAVAILABLE`, `ON_COLLECTION`, or `OFFLINE`. Admin assignment currently chooses a candidate by distance then workload; material qualification and request-priority allocation are not represented in this candidate logic.
- A collection request has one material and one total weight. Status events provide lifecycle timestamps; assignment records hold assignment/accept/decline data. Collector reads currently omit declined and cancelled history.
- Facility verification currently moves `VERIFICATION_PENDING` to `VERIFIED`, awards recycler points idempotently, and notifies the recycler and Admin. Keep this cross-role workflow intact; do not award rewards twice or mark a request verified before facility verification.
- Collector assignment notifications are created, but the existing notifications read endpoint is Recycler-only. No simulator integration was found in the repository. The existing map/navigation experience is already used by collector pickup actions.

## Scope and implementation constraints
- Read the current `AGENTS.md`, `client/AGENTS.md`, `PROJECT_CONTRACT.md`, relevant tests, Prisma schema, and the installed Next.js guidance required by `client/AGENTS.md` before editing application code.
- Preserve existing auth/session behavior and the Admin, Recycler, and Facility workflows. Enforce role and ownership restrictions in server handlers, not only in the UI. Collectors may access only their own profile, notifications, and job data; do not expose Admin, other collectors' private data, reward administration, facility administration, simulator administration, or audit administration.
- Reuse the existing collections routes, assignment/profile/status/weight/notification models, map/navigation, and polling. Add only the smallest schema/API changes needed for missing data, with a Prisma migration and generated client where required.
- Treat the backend as authoritative for availability, assignment eligibility, transitions, weight/material validation, and ownership. Keep location privacy: a collector can receive the collection location, but recycler-facing APIs/UI must never expose exact collector GPS coordinates.
- No external simulator service or contract is present in this repository. Do not invent an endpoint, claim to control physical sensors, or add a browser-only timer as simulator integration. If no real simulator contract/configuration is provided, preserve the user-facing “Waste Cleared” notification and leave an explicit, documented integration boundary rather than reporting a simulator reset as successful.
- Keep existing facility verification and reward idempotency semantics. Completing collector work must hand off to facility receiving/verification; only the existing authorized verification flow awards rewards.

## Collector experience
- Upgrade the existing collector dashboard to show persisted availability (`ONLINE`, `OFFLINE`, `BUSY`, `UNAVAILABLE` labels mapped consistently to existing availability values), active and pending jobs, today's and lifetime collected kg, completed count, and average response time. Add a server-backed availability update; OFFLINE/UNAVAILABLE collectors must not receive new assignments. Do not let a manual availability change make a collector eligible while they have active work.
- Show assigned/available work with collection ID, area/address, material(s), estimated weight, priority, distance when available, and creation time. Make HIGH and CRITICAL work visually prominent. Keep the existing Admin-assignment path operable while adding any automatic assignment path.
- Implement automatic assignment on the backend, with an atomic eligibility check. Require approved/active collectors who are available, within service area, and qualified for the requested material. Process higher-priority requests before lower-priority requests; for eligible candidates apply closest-first and then least-active-workload tie-breaking. Derive priority/qualification from existing authoritative data where possible; introduce minimal validated persisted fields only if none exist. Never trust client-supplied eligibility or ranking.
- Accept: atomically transition an assignment once, record collector and timestamps, and notify the requester and Admin without duplicating existing notifications.
- Decline: require a reason code (`VEHICLE_FULL`, `TOO_FAR`, `UNAVAILABLE`, `MATERIAL_UNSUPPORTED`, `SAFETY_ISSUE`, `OTHER`) plus optional explanation. Reject blank/invalid codes server-side, retain the audit/status history, notify Admin, and reassign to the next suitable collector when eligible candidates exist. Preserve useful requester communication.
- Navigation must use the existing map/directions implementation and collection coordinates/address. Add a clear Navigate action that starts the existing simulator flow only if a real integration is discovered; otherwise it must not falsely claim that travel was simulated. Backend status remains authoritative and is reflected by existing polling. Recycler tracking continues to show only “Collector is on the way” and ETA, never exact collector GPS.
- Preserve accepted -> en route -> arrived -> collecting -> paused/resumed -> handoff transitions. Require a delay code when pausing (`VEHICLE_PROBLEM`, `SAFETY_ISSUE`, `SORTING_DELAY`, `CUSTOMER_DELAY`, `OTHER`) and explanation if supported by the existing interaction. Record pause/resume/start/arrival timestamps in existing status events or the smallest suitable existing record.
- Replace the single-weight close control with a validated close-task form that records one or more valid material categories and non-negative numeric kg per category, total weight, optional notes, and optional proof photo. Keep photo handling within existing supported upload/storage capabilities; do not store a fake local URL as proof. Validate on both client and server. Handoff the completed pickup to the existing facility verification workflow and notify the requester that the waste was cleared.
- Add collector history for completed, declined, cancelled, and paused jobs and performance metrics from real backend records: completion count, collected kg, average response time, average collection duration, decline count, and cancellation count. Return only the signed-in collector's data.
- Expose the signed-in collector's notifications, including assignment, priority change, cancellation, reassignment, facility issues, and Admin messages where those events already exist. Poll new jobs, status changes, cancellations/reassignments, and notifications every 2-5 seconds without full-page reloads; avoid duplicate timers/requests and stale updates.
- Keep actions prominent and ergonomic on mobile. Reuse existing components and Tailwind conventions; handle loading, empty, error, disabled, and success states accessibly.

## API, schema, and security
- Add typed client API functions and server-side schemas for availability, decline codes, pause reasons, per-material weights/notes/proof references (only if supported), collector history/performance, notifications, and backend assignment as needed.
- Keep collector reads filtered by authenticated user ID. Ensure every mutation verifies role, approved profile, active assignment ownership, and legal current status. Add regression tests proving a collector cannot read/update another collector's jobs/profile/notifications or access Admin-only routes.
- Use transactions/conditional updates for assignment and lifecycle transitions to prevent double assignment and duplicate completion/reward effects. Keep notifications and status events transactionally coupled where the existing design does so.
- Keep Admin-created assignments functional and route assignment/reassignment through one eligibility/ranking implementation rather than duplicating rules.
- Update `PROJECT_CONTRACT.md` API contracts if endpoint methods/shapes change. Do not edit `.env` or expose secrets.

## Verification
- Add or update focused tests for eligibility/ranking, assignment races and reassignment, availability blocking, valid/invalid decline and pause reasons, status transitions, per-material weight validation, own-data access controls, notification scoping, and performance calculations.
- Run `npm run test:api`, `npm run prisma:validate`, and `npm run api:build` from `server/`.
- Run `npm run lint` and `npm run build` from `client/`.
- Manually test as Collector, Recycler, Facility, and Admin: online/offline assignment, accept/decline/reassign, navigate/arrive/start/pause/resume, multi-material close, facility verification and rewards, user-facing tracking privacy, collector history/performance/notifications, and polling updates. Report simulator integration as unavailable unless an actual service contract is found and successfully exercised.
- Finish with changed contracts/migrations, checks run, and exact manual test steps. Do not claim unsupported simulator, GPS-routing, photo-upload, or physical sensor behavior.
